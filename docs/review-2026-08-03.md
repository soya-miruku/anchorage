## 0. Remediation status (updated after the review)

This document was written as an audit snapshot. A substantial part of it has since been
fixed. **The findings appendix is deliberately left as the original snapshot** — it records
what was true at review time, not what is true now.

App test suite: **223 → 277 passing**, plus 78 Go test functions. Race-clean, typecheck clean,
production build green, and the design gate passing 24/24 (worst state 1.61% MAE against a 2%

**The rest of the evidence bundle is stale and preflight has not been re-run since the
archive and tag work landed.** The capability ledger, mutation matrix, read-only acceptance,
30-minute performance soak and host candidate were all generated against an earlier core
binary. They are expected to pass — the changes are additive and the new verbs were verified
live against the real daemon — but expectation is not evidence, and this project has already
had one run attest to a stale binary.

| **Image push** | `docker push` as a confirmed session. **Anchorage never handles a registry credential** — the Docker CLI resolves them from the operator's own configuration and helpers, so nothing secret enters the renderer, crosses IPC, or is stored; a test asserts the dialog contains no password field. Confirmation lives in the core, not just the UI, because push is the only verb that sends something outward and its destination is *derived from the reference* rather than chosen — a mistyped tag publishes to a registry nobody intended, which is a disclosure rather than a failed command. The dialog leads with the destination host, and a reference with no registry host is called out as resolving to public Docker Hub. | **Security audit of the new surfaces** | An audit of the archive, compose, volume-browse, tag and Scout code found twelve items; all are closed. Two were confirmed exploitable by reproducing them: `compose up` would read its Compose file from the renderer's own stdin (`--file /dev/stdin` plus `session.input`, yielding arbitrary privileged containers), and `docker scout` accepts `fs://`, so a reference could inventory the operator's home directory and ship the SBOM to a network CVE service. Config paths must now be ones Compose itself reports for the project, and source schemes are refused. Archive writes could silently truncate an existing host file and the validator *rejected* `confirmed`, so replacing a file now takes an explicit `overwrite`, the final path component is `Lstat`ed so a symlink cannot redirect the write, and devices are refused. The volume helper's label promised a sweep that did not exist; one now runs before each browse and on a lost create response. Four CLI call sites bypassed argv validation and now share one validating helper. Scout and volume browse were unbounded in concurrency and are now admitted through semaphores that fail fast. `compose down --volumes` no longer rides on `down`'s confirmation. Compose, save/load and export emitted no domain receipts at all, so nothing driven off `operation.*` saw them finish — they now share image pull's receipt emitter, with both the schema and the renderer event validator taught the domains and actions involved. |
| **Scout vulnerabilities** | `images.scout` runs `docker scout cves --format sarif` and projects the SARIF so the renderer never parses SARIF itself: a severity summary (every severity present even at zero) plus findings ordered worst-first, each carrying the package, the version installed and the version that fixes it — the only actionable field in a vulnerability report. Scout's literal `"not fixed"` is rendered as "no fix available" rather than as a version to upgrade to. **Never runs automatically**: measured here, the first analysis of a 1 GB image took 2m16s because Scout indexes it, while a second run returned in 2.0s from its cache — so opening a detail panel must not trigger one. Findings are capped at 500 so one badly outdated image cannot exceed the transport's line limit; the summary count is never capped. Scout accepts an immutable image ID as well as a tag, so dangling images can be analysed too. |
| **Volume browse** | Volumes can be opened, navigated and previewed. Docker exposes no way to read a volume directly, so the core mounts it **read-only into a helper container that is created and never started** — the archive endpoint reads a container's filesystem whether or not a process ever ran in it, so browsing executes no code at all. The tar-header walk and single-file read were extracted from the container file browser rather than duplicated. The helper is removed through a detached context so a cancelled browse still cleans up; a leaked helper would hold a reference on the volume and silently block its removal. Docker **implicitly creates** a volume when a bind names one that does not exist, so the volume's existence is confirmed first — without that, browsing a mistyped name silently created an empty volume, which a read must never do. |
| **Archive transfer** | `docker image save` / `load` and `docker export` end-to-end. All three run as cancellable sessions writing straight to a host file through Docker's own `-o`/`-i`, because a saved image is routinely gigabytes and cannot transit the JSON transport. The archive path is validated at all three boundaries — absolute, never leading `-`, no control characters, parent directory canonicalized against the working-directory allowlist, and `load` additionally requires the file to exist. Save is reached from image detail (only where a reference exists — a dangling image cannot be named on the command line), Load from the Images toolbar, Export from container detail. Pull's session-following logic was generalized rather than copied, so all four transfers share the same event buffering, output acknowledgement and cancel-on-restart behaviour. |

### Still outstanding

**Buildx is not installed on the development host**, so the Builds screen cannot be built
against the surface Docker Desktop uses for it: `docker buildx` is an unknown command there,
and `docker build` reports itself as the deprecated legacy builder. The screen renders empty
rather than fabricating data. Scout v1.18.3 *is* installed and is not yet surfaced.

**Operator-environment finding, outside the codebase:** on the development host
`~/.docker/config.json` is world-readable (`-rw-r--r--`) and holds inline base64 credentials
for Docker Hub and a private registry, with no credential helper installed. Base64 is
encoding, not encryption, so any local process can read them. This is why push delegates
rather than storing anything itself, and it is worth fixing independently (`chmod 600`, plus
a credential helper).

**Product:** Volume **upload** is not implemented: the helper mounts read-only, deliberately, and writing would need a second
lifecycle with different failure semantics. Image mutation verbs (`push`, `import`,
`manifest`) — `push` needs
registry auth, which has deliberately not been wired: it would mean transmitting credentials,
and that is a decision to take explicitly rather than in passing. The Command Center already
reaches `docker push` through the operator's own credential helpers ·
Builds screen still fixture-only (the largest remaining piece) · volume browse, which needs a
helper container as Docker Desktop does · volume detail view · exec hardcoded to `/bin/sh` ·
container Stats remains native-transport-only on CLI-fallback contexts (the dashboard no
longer is) · most of the 74 medium and 59 low findings.

**Archive paths are not sandboxed in production.** The core checks an archive's parent
directory against its working-directory allowlist, but the desktop launches the core with
`--allow-cwd /` (see `app/electron/core-launch-policy.mjs`), so in the shipped configuration
that check reduces to "the parent exists and resolves". The effective boundary is the OS: the
core writes as the invoking user, exactly as `docker save -o` would. The allowlist genuinely
contains the path only when the core is launched with a narrower root. The validation that
does hold in every configuration is the argv-shape check — absolute, no leading `-`, no
control characters — which is what stops a path from being re-read as a Docker flag.

**Verification debt found the hard way:** three claims made during remediation were wrong and
were caught only by end-to-end gates, not by unit tests — per-request cancellation killed
every session (caught by the 30-minute soak), a mutation run attested to a stale binary
(caught by the evidence hash gate), and the session fix missed the `imagePull` call site
(caught by the mutation suite). The acceptance matrix still has no check that holds a session
open, which is why the first of those survived 18 passing checks.

**Release:** the AppImage is unsigned and there is no update channel — both need a
project-owned signing key.

## 1. Verdict

Anchorage is a **well-engineered transport with a thin product on top of it**.

The Go core, the JSONL RPC layer, the preload/main contract validators and the session/PTY
machinery are genuinely good — better than most Electron Docker GUIs. The confirm gates,
immutable-ID requirements and argv validation are real server-side checks, not renderer
theatre. That part of the codebase should be preserved as-is.

The renderer exercises a fraction of what the core already implements, and against real
Docker it is not yet a daily driver. Three things block calling it a Docker GUI:

1. **Whole management domains are absent** — networks, `system prune`, compose, container
   creation, context switching. *(Networks and `system prune` have since been implemented;
   compose, container creation and context switching remain.)*
2. **The deletion surface that exists is gated, mislabelled, or dead** — no force anywhere,
   no bulk select, no size preview, no undo, and two destructive buttons that do the wrong
   thing. *(Fixed, except bulk select and undo.)*
3. **Live state is unreliable** — Command Center mutations invalidate nothing, the inspect
   cache is wiped by any reconciliation event and never refetched, the CPU/MEMORY columns
   are permanently `—`, and the Stats history charts are erased every two seconds.
   *(Inspect cache and Stats history fixed; Command Center invalidation and the CPU/MEMORY
   columns remain.)*

A recurring theme: **the documentation and evidence artifacts measure the wrong thing.** The
capability ledger's headline "219/219 covered" resolves to *219 of 219 leaves routed to a
raw-argv palette*. That is evidence of how much of Docker has **no first-class surface**, not
of parity. `docs/parity-and-release-gates.md` is scrupulously honest about the distinction;
the number is still routinely read as a parity claim.

Realistically: **strong plumbing, roughly a third of the product.**

## 3. The removal / deletion question

This was the original question, so it gets answered first and precisely.

### Containers

Removal **is** implemented end-to-end — protocol, both Go transports, both validation
layers. It is the **renderer** that throws it away.

- `app/src/utils/containerPresentation.ts:92-94` — `canRemoveContainer` returns true only for
  `created | exited | dead | stopped`. The Delete button is therefore permanently disabled
  for every **running, paused, restarting, removing and unknown** container, with no tooltip
  explaining why.
- `app/src/services/anchorageBridge.ts:842-845` — the bridge hardcodes the options to
  `{ confirmed: true }`. `force` and `volumes` — fully specified in `protocol/types.ts:85-92`,
  validated in `preload.cjs` *and* `contracts.mjs`, and implemented on both Go transports —
  are **unreachable dead code**.
- Consequence: `docker rm -f` and `docker rm -v` cannot be performed from the UI at all.

**A paused container is a complete dead end**: Stop is disabled, Delete is disabled, and no
unpause action exists anywhere in the product. Only Restart is available.

### Images

- `app/src/screens/ImagesScreen.tsx:61-66` gates the delete button on
  `!image.usageKnown || image.inUse || !image.reference`. **Measured on this host: 221 of 232
  rendered rows have a delete button that can never be clicked** — 178 because they are
  dangling (`reference === null`), 43 more because they are in use. Eleven rows are clickable.
- `app/src/store/useAnchorageStore.ts:1336` re-blocks the same condition, so even enabling the
  button would not help.
- The protocol has **no remove-by-ID shape**: `protocol/types.ts:115-126` requires *both* `id`
  and `reference`, and `domain.go:1319-1325` enforces both. Dangling images have no reference,
  so they are structurally unreachable — the only escape is an all-or-nothing dangling prune.
- `force` and `noPrune` exist in protocol and core (`domain.go:973-974`, `:1116-1121`) and are
  **never sent** by the renderer.
- `app/src/services/anchorageBridge.ts:911-912` hardcodes `includeDangling: true`, inverting
  Docker's own default — the screen shows 232 rows where `docker image ls` shows 54, with no
  filter, search or sort.

### Processes

`docker top` **does not exist in host mode**. The only process list in the product is a canned
`ps aux` string in the browser-mode fixture. There is also no `pause`, `unpause`, `kill`
(or signal delivery), `rename`, `update`, `attach`, `cp`, `diff`, `export`, `commit`, `port`
or `wait` — the Go core's container action allowlist is exactly
`start | stop | restart | remove` (`core/internal/core/engine.go:596-603`).

### Two destructive buttons that do the wrong thing

- **Volume "Clean up" is hardcoded to `--all`** (`useAnchorageStore.ts:1670-1676`). A button
  labelled "Clean up", behind a single native `window.confirm`, destroys **every named unused
  volume** — 198 of them on the reference host — including the data volume of any stopped
  database.
- **Images "Clean up" prunes only dangling images** while the header advertises 166 unused,
  and the Dashboard's "Prune images" button is a **silent no-op** when nothing is dangling.

### And one that does nothing at all

**"Create volume" is permanently dead in the packaged AppImage.** `VolumesScreen.tsx:5-8`
calls `window.prompt`, which Electron short-circuits to `null` in the renderer. Clicking it
produces no dialog, no error, no toast. The renderer tests mask this by stubbing the exact
browser global that does not exist in the host.

### Object-type coverage

| Group | First-class UI | Notes |
|---|---|---|

Everything not first-class is reachable only by hand-typing literal argv into the Command

### Missing GUI affordances

No multi-select, no bulk actions, no column sorting, no per-row overflow menu, no port
link-opening, no copy-ID, no image detail view, no volume detail view, no created/age column,

container every 2 s).

### Degraded transports

`system.snapshot` and `containers.stats` are **native-transport-only**
(`domain.go:33-42`, `:426-435`). On any context resolving to the CLI transport — the common
remote/SSH case — the entire Dashboard and the entire Stats tab become unavailable. Volumes
become permanently read-only on the same contexts.

## 5. Security

The Electron and core boundaries are **above average for the ecosystem**. Most findings are
about packaging and about documentation overstating what was verified — not about renderer
escape.

### The real issues

**The shipped AppImage disables the Chromium OS sandbox.** The embedded `.desktop` entry is
`Exec=AppRun --no-sandbox %U`. `webPreferences.sandbox: true` (no Node in the renderer) and
the Chromium OS sandbox (seccomp-bpf + namespaces) are *different controls*, and the evidence
artifacts conflate them. Any desktop-integrated launch runs the renderer with no OS-level
containment. Fix: `linux.desktop.entry.Exec: AppRun %U` in `electron-builder.yml`, plus a
packaged-smoke assertion that fails if `--no-sandbox` is in `process.argv`.

**Unsigned release with no update channel.** No signature, no `.sha256_sig`, no update feed.
Users cannot distinguish a genuine build from a trojaned one, and an installed copy will run
Chromium 150.0.7871.129 forever — there is no path to deliver the next Chromium security fix.

**`cli.run` / `session.start` accept arbitrary docker argv.** This makes every structured
confirm gate and immutable-ID requirement bypassable *by design* — the renderer is a fully
trusted control surface, and anything that compromises it obtains
`docker run --privileged -v /:/host`, i.e. host root. This is a defensible architecture (the
user's own shell already has docker access), but `docs/architecture.md` should state plainly
that the Electron/Go split is a **process-isolation and correctness boundary, not a renderer
containment boundary**.

**Live-host evidence artifacts are committed with no redaction** anywhere in the generation
pipeline, and the packaging pipeline **never runs `npm ci`** — the dependency evidence binds
lockfile bytes, not the installed tree. There is no Go toolchain/stdlib vulnerability gate,
and the dependency audit covers zero shipped runtime code.

**No aggregate payload cap on `cli.run` / `session.start`** — one IPC call can force hundreds
of MB of main-process allocation.

### Verified as genuinely sound

- `sandbox: true`, `contextIsolation: true`, no node integration, CSP set, all permissions
  denied, `window.open` denied, untrusted navigation denied, all downloads blocked
  (`security-policy.mjs:10-25, 111-118, 151-160`), asserted at runtime in the packaged smoke
  (`main.mjs:487-493`).
- The preload's `invoke` is an **allowlisted switch, not an escape hatch** (`preload.cjs:943`).
- `contracts.mjs` is a genuine **second** validation boundary, not a pass-through —
  `assertOnlyKeys` rejects unknown keys including `__proto__`.
- Argv construction is **injection-proof on structured paths**: `validateImageReference` and
  `validateVolumeName` both reject a leading `-`, container IDs are 64-hex, image IDs are
  `sha256:`-prefixed, and `exec.Command` always receives the resolved `binary.RealPath`.
- The image tag→ID re-resolution safety check described in `docs/architecture.md:190-191` **is
  implemented** on both transports (`domain.go:943-971`, `:1088-1114`). It is check-then-act
  against a mutable name, so it is not TOCTOU-safe — but it is real.
- Electron 43.2.0 is the **current** npm `latest` (Chromium 150.0.7871.129) — no currency gap.
  `npm audit` reports 0 vulnerabilities across 512 dev dependencies, all with integrity hashes
  and no non-npmjs `resolved` URLs.
- The Go core is **genuinely stdlib-only** — no `go.sum`, no `vendor/`, no `replace`,
  statically linked with no dynamic section (confirms `CGO_ENABLED=0`).
- The evidence hash chain is **real and current**: every sha256 in `app/build/core/manifest.json`
  recomputes correctly, and the "223/223" test count reproduces exactly.
- Command Center secret handling is thoughtful — `commandCenterModel.ts:57-92` detects
  secret-bearing argv positions (including `docker login -p`), masks the value, excludes it
  from history and disables copy.
- No on-disk persistence of Docker-derived data anywhere; the only `localStorage` use is the
  appearance preference.

## 6. Performance

### Core — the dominant cost is rediscovery, not Docker

Measured against the real binary and live daemon:

| Path | Measurement |
|---|---|
| `containers.list` warm | **27.6 ms**, of which the actual `/containers/json` is **5.3 ms** — **81% is rediscovery overhead** |
| Per-RPC overhead | re-forks `docker context inspect` (12.9 ms) + builds a fresh `http.Transport` + throwaway `GET /version` (7 ms) + `CloseIdleConnections` |
| At the 2 s poll cadence | **30 docker CLI process spawns per minute** (~43,000/day) |
| `system.snapshot` | **hard-fails with `engine_timeout` after 60.1 s** on this host — calls unfiltered `/system/df`; runs on engine-ready **and after every mutation** |
| `volumes.list` | 3.08 s `/system/df?type=volume` **on every call**, polled every 10 s |
| `images.list` | two full `shared-size=true` `/images/json` requests, 943 ms warm |
| `system.capabilities` | **244 `docker … --help` subprocesses**, 2.69 s, 389 KB response line — awaited *before first real data* and re-run on every Command Center open, with no cache |

The SHA-256 binary fingerprint is **not** on a hot path (`service.go:53`, once) — that one is
fine.

**No per-request cancellation exists** (`rpc/server.go:88-96` hands every handler the
process-level context). Abandoned RPCs run to completion holding goroutines, sockets and
subprocesses. Session output and control responses share one unbuffered stdout pipe behind a
single mutex — head-of-line blocking.

**Confirmed leak.** A session whose output exceeds the ack window and stops being acked wedges
permanently: the child exits, `session.exited` is never emitted, `session.cancel` returns
`accepted:false` and does nothing. Three wedges leaked **+5 fds and +8 OS threads**. Any
renderer reload or dropped subscription during streaming triggers it.

### Renderer — no subscription architecture at all

`useAnchorageStore` is one hook with 43 `useState` calls returning a fresh 93-key object
literal on every render (`useAnchorageStore.ts:1853-1950`). There is **zero `React.memo`,
`createContext` or `useSyncExternalStore` anywhere in `app/src`** (verified by grep).

Every 2 s container poll, every 1 s clock tick, every log chunk, every image-pull chunk and
every `hostDomainState` transition re-renders the **entire tree** — titlebar, sidebar, engine
card, status bar, active screen, and the Command Center dialog if open. Baseline ~2 full-tree
renders/sec idle, ~3/sec on the Stats tab.

Virtualization is partial: `FixedRowWindow` re-renders per raw scroll event with no throttle
and no ARIA, and **the Volumes list is not virtualized at all** despite
`docs/architecture.md:53` claiming large lists are.

The build is clean of source maps and correctly code-splits xterm (332 kB lazy chunk), but the
entire browser-mode fixture corpus and `FixtureBridge` ship inside the 396 kB production
chunk — and `createAnchorageBridge` **silently falls back to fabricated Docker data** if
`window.anchorage` is ever missing in the packaged app.

### Evidence gaps

`artifacts/performance/results.json` never measures `system.snapshot` or `system.capabilities`
— the two slowest paths — never runs polling concurrently with the RSS soak, and its
30-minute "streaming soak" is `docker events` at 13 KB/s (7.4 events/s), three orders of
magnitude below a chatty `docker logs -f`. It therefore never exercises backpressure,
head-of-line blocking, or the wedge above.

## 7. Correctness defects

The highest-value ones, all with a concrete failure scenario:

1. **Any container reconciliation event wipes the whole inspect cache and nothing refetches**
   (`useAnchorageStore.ts:570-577`; `:693` is the only fetch site). A mutation issued from a
   *terminal outside the app* is reconciled by the core and permanently blanks the Inspect and
   Bind-mounts tabs.
2. **Logs are fetched exactly once per container per app run.** Host `logs` is a one-shot
   `cli.run` (`anchorageBridge.ts:1000-1008`); "Follow" never streams and is affirmatively
   misleading. "Clear" poisons the cache permanently — navigate away and back and the pane is
   still empty.
3. **Stats history charts can never accumulate.** Two independent 2 s writers own the same
   state: the stats sampler appends to `cpuHistory`, and `refreshContainers` replaces the whole
   array, resetting it to `[]`. The advertised 48-sample window never fills.
4. **CPU% is a lifetime average, not a live rate** — `domain.go:439-441` sets both
   `stream=false` *and* `one-shot=true`, so `precpu_stats` is never populated. Empirically
   **wrong by 8×–50×** against the same daemon. Dropping `one-shot=true` fixes it.
5. **Dashboard disk figures double-count shared layers.** Summing per-image `Size` repeats
   every shared parent. Reports **132.99 GB reclaimable / 164.66 GB images** where
   `docker system df` reports **9.336 GB / 71.24 GB** — wrong by 14× and 2.3×. The daemon
   already returns the correct aggregates in the same response.
6. **Command Center mutations invalidate nothing**, and there is no manual refresh anywhere.
7. **One transient poll failure permanently stops polling** and replaces the entire UI with a
   full-screen error — no tolerance threshold, no backoff.
8. **Log following and the Exec PTY never recover after a core restart** — they freeze silently
   while the UI reports healthy.
9. **`domainCLIOutputLimit` (16 MiB) exceeds the 8 MiB JSONL line cap**, so a large CLI-fallback
   mutation receipt makes Electron SIGTERM the core.
10. **Multi-byte UTF-8 split across a 16 KiB read boundary** is corrupted into replacement
    characters in all live output views.
11. The shipped titlebar **hardcodes version "4.31.2"** in host mode while the product is 0.1.0.

## 8. Strengths to preserve

Do not refactor these away while fixing the above:

- **Server-side mutation safety is real.** Full 64-hex container IDs (`engine.go:582-594`),
  `Confirmed` required for remove (`:613`), `sha256:`+64hex for image IDs
  (`domain.go:1412-1422`), and re-inspection of the reference before deletion
  (`:962-971`). A stale UI row cannot become a delete of the wrong resource.
- **Argv construction is injection-proof on structured paths** — the class of bug most Docker
  GUIs ship with.
- **Dual-transport with honest degradation** — every domain method tries the Engine API and
  falls back to fingerprinted CLI JSON, recording limitation strings rather than fabricating.
- **The session/PTY transport is the best-built thing in the repo** — cumulative byte-window
  acknowledgement, truncation events, `Setpgid` process-group management. It is *under-used by
  the product, not under-built*.
- **The preload/main contract layer is a genuine second boundary**, duplicating validators
  rather than trusting the renderer.
- **Host mode refuses to fake data** — Builds, Extensions, Dev Environments and container Files
  all render `UnsupportedSurface` against real Docker. Many projects would have shipped the
  fixture. This discipline is worth keeping.
- **Command Center secret handling and focus management** — it has the only correct modal in
  the app (focus trap with restore-on-close, two-step destructive confirm).
